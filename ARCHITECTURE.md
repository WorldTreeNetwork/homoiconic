## Partition

| Language | Role | Contains an evaluator? |
|---|---|---|
| Lean 4 | The only semantics language. The evaluator, `Reflect`, is Lean 4 source, and the proofs talk about that source. | Yes. This is the only one. |
| Zig | The host: the operating-system process. It handles files, allocation, and the REPL. It loads the Lean runtime and returns the kernel's result. In the machine image it is also the layer that stands where an operating system would. | **No.** It never re-states the semantics or grows a second `eval`. |
| Rust | Absent. It is not a language of the first system. | n/a |

## Circularity

Circularity means the interpreter theorem. An interpreter is a term of the language. For every program, evaluating that term on the program as data equals evaluating the program directly. The theorem is `reflective`, proved about `Reflect`, the evaluator that runs, with no fragment. Its statement is in `openspec/specs/code-as-data/spec.md`.

The first kernel, `Circular` (`add-lean-circular-kernel`), proved the theorem for quote-free programs at one level; `retire-circular-kernel` deleted it, and it is in git at `8b23867` and earlier.

## Reflect

The kernel package holds three Lean libraries, `Reflect`, `Wire` and `Surface`. `Reflect` is the language, its one evaluator, and its proofs. In `Reflect` a program is a data value: data is natural numbers, arrays, text and names, and quoting a program is a literal of its data form. The interpreter is one closed term that takes a program as data, and the interpreter theorem holds for every term, with no fragment. A stack machine runs the same language one step at a time, and it is proved equal to direct evaluation. The statements are in `openspec/specs/code-as-data/spec.md` and `openspec/specs/bytecode-machine/spec.md`.

`prim c x` runs an operation from a table, `Ops`: one total function from an operation number and a data value to a data value, and the cost a priced budget charges for it (one unless the table says; `arithCost` for arithmetic). Only `runPriced` reads the cost, and only the run command uses it (`homoiconic-q59.52`). Evaluation, the interpreter theorems and the machine theorems are stated for every table. The interpreter is the same term for every table, so a new set of operations is added to a table with no new proof. The first table is exact arithmetic (`kernel/Reflect/Arith.lean`), and the host runs with it (`add-operation-tables`).

Text and names are kinds of data, added without editing the interpreter (`add-data-kinds`). The interpreter tests a value only with its own `case` and builds its answer with its own `succ`, `cons` and `prim`, so a new kind must be seen by `case` as a number or as a list and go `wrong` exactly where that view does. A text is seen as the list of its code points: `case` gives the first code point, a number, and the rest, a text, and `cons` onto a text gives an array. A name is seen as its number by `case`, `succ` and the operation number of `prim`, and by nothing else: `succ` of a name is a plain number, and an arithmetic operand that is a name is not a number. Equality tells a text from an array and a name from a number. `Direct` gained twelve rules and no existing rule changed; `interp` and `evalTerm` are the same terms, and `reflective`, `reflective_coverage`, `reflective_env` and `tower` were proved again with their statements unchanged. A text is a `List Char`, behind the three functions of `kernel/Reflect/Text.lean`; a character is a list cell in memory, and the representation is left for later. The first table gained `text` (7) and `codes` (8), between a text and the array of its code points.

## Requests

A program can ask the outside for something and continue from the answer. A request is an ordinary value: `ask payload next` builds a function that hands its payload and the rest of the program to its caller. Nothing is added to the language, evaluation, the interpreter or the machine. A driver outside the program runs it against a list of answers: every function a turn ends in is read as a request, its payload must be data, and the rest of the program runs on the next answer. The driver is defined once, over any way of evaluating, and it is proved that a run is fixed by the program and the answers, and that direct evaluation, the interpreter on data and the machine make the same requests and end the same way. A request carries no mark, so a driven program cannot finish with a function. What a payload means is not part of this. The statements are in `openspec/specs/requests/spec.md`.

## Channels

Several programs can run side by side as processes in one machine and talk over channels. Nothing is added to the language: a process is a program that makes requests, and four shapes of payload are channel requests. `[0]` makes a channel and is answered with its name, a name value: a kind of data that carries a number. `[1, name, message]` sends and `[2, name]` receives when `name` is a name value; with a number there they are requests to the outside. `[3, program, start]` starts a quoted program on the data `start` as a new process. Every other payload is a request to the outside. A send and a receive meet in one event; there is no queue. A schedule is a list of events, and the new names and the answers from outside are events, so the schedule is the whole record of a run. A process holds the names it made, the names its starter held that occur as name values in its start data, and the names a sender held that occur as name values in a message it received and that it does not hold already, and it can send or receive only on a name it holds. A number hands over nothing, and the program of a start request is not searched. It is proved, for every table, that a program and a schedule lead to at most one configuration (`network_deterministic`), that a process uses only names it holds, every held name was made by an event of the schedule, and no process holds a name twice (`Network.held_nodup`), that the machine runs a schedule as direct evaluation does, that the interpreter on data does too (`network_reflective`, `network_interpreted_exact`), and that what the executable scheduler reports is a run of the program. Holding is kept by the scheduler, as a list of numbers; events and schedules hold numbers too. A name is a kind of data, not a number, so a number that occurs in quoted code or a message is no longer handed over as a name (`add-data-kinds`). It is still not a key: holding is the scheduler's list, and a process can have a name value it does not hold, spliced into its code or answered from outside, and cannot send or receive on it. That a program cannot come to have such a value is not claimed. The interpreter on data is covered at one level, with the scheduler outside it; the interpreter interpreting itself over a schedule is not stated. A set of processes cannot be kept on disk. The command `host/out/chan` runs a program as the first process and prints the schedule it went through; given that schedule back, it runs the same events. The definitions are in `kernel/Reflect/Channel.lean` and `kernel/Reflect/ChannelProof.lean`, the exact statements in `kernel/ChannelContract.lean`, and the requirements in `openspec/specs/channels/spec.md`. One program has a channel whose other end is another network guest (`kernel/Surface/Remote.lean`, `examples/remote.hom`): its first send, a quoted function and a reply name, leaves as bytes over QUIC, the other guest runs the function to its first send and answers on the reply name, and the sender checks the answer against its own Lean. The log it prints is the one-machine schedule, not a record of the two guests' deliveries (`homoiconic-q59.51`). That a remote machine cannot forge a name is a hypothesis, not a theorem.

## The log

A VM is a program that makes requests, together with the identifiers of the log entries it has acted on. A log is a list of entries, each an identifier and an answer. Handling an entry answers the request the VM is waiting on and records the identifier; an entry whose identifier the VM has acted on changes nothing, and neither does any entry once the program has finished. The state of a VM is the fold of handling over its log, so the log is the record and the state can be made again from it. It is proved, for every table, that a program and a log lead to at most one state, that the state after a log is the state after a prefix carried on through the rest, that an entry already in the log changes nothing, that a state reached by a first part of the log and then given the whole log reaches what the whole log reaches from the start, that the run is the request driver's on the answers of the first deliveries, and that the machine and the executable fold agree with direct evaluation. A log that is read is sealed: an entry is written as a mark and an answer, and its identifier is the Blake3 hash of those two together, computed by the kernel (`Surface.Keep.entryName`). The mark is not read; it tells apart two entries with one answer, and is where a count, a link to the entry before, or a signature can go. It is proved that two sealed entries with one identifier are one entry, and so that no entry of a sealed log is passed over for a different one, for every naming function that gives different names to different data; that Blake3 is such a function is assumed, as it is for stored pieces. Nothing is signed. An entry does not say which request it answers, so the order of first deliveries decides the state. `Surface.Keep` handles a log against a store and saves the state under one root; `host/out/vm` starts a program on a log or hands a log to a kept state. That the session ends holding the state the theorems speak of is tested, not proved. Given that, it is proved that a restarted state has the root a replay from the start has (`Surface.Keep.restart_same_root`): what saving leaves and the root it gives depend only on the value a partial piece stands for, when every reference in it was made by saving (`kernel/Wire/PieceProof.lean`, `kernel/RootContract.lean`). Nothing is assumed of the hash for this. It does not hold of a piece that holds the root of a small piece, which a turn of `keep` can leave (`openspec/specs/wire-bytes/spec.md`). The definitions are in `kernel/Reflect/Log.lean` and `kernel/Reflect/LogProof.lean`, the exact statements in `kernel/LogContract.lean`, and the requirements in `openspec/specs/event-log/spec.md`.

## Nodes

A node joins the two: several processes whose schedule is a log. An op is an event of the scheduler with an identifier, and a node is a configuration of processes together with the identifiers of the ops it has acted on. Applying an op the node has acted on changes nothing; otherwise the event happens as for a schedule. An op whose event cannot happen has no next node, because a log is the record of what happened. An op that is read is sealed as an entry is: its identifier is the hash of its mark and its event as written. It is proved, for every table, that a program and a log lead to at most one node, that an op already in the log changes nothing, that a node reached by a first part of the log and given the whole log reaches what the whole log reaches from the start, that a node's processes are where the schedule of first deliveries leads (so the channel theorems hold of them), and that the machine and the executable `nodeRun` agree with direct evaluation. An event is also split into the machine runs it needs and the configuration once they end (`plan`), and that split is proved to be the event, both ways. `Surface.Keep` applies a log to processes against a store using `plan`, and saves the node under one root; `host/out/node` starts a program on a log or applies a log to a kept node. The session, and that a restarted node has the root a replay has, are tested, not proved. The definitions are in `kernel/Reflect/Node.lean` and `kernel/Reflect/NodeProof.lean`, the exact statements in `kernel/NodeContract.lean`, and the requirements in `openspec/specs/logged-processes/spec.md`.

## Stored state

A running program's state can be held in pieces. A piece is a number, a text, a name, an empty list, a pair, a function, or a reference to another piece, and one type serves for data, values and environments. A text and a name are leaves: the lazy machine takes a text apart, and sees a name as its number, with no fetch beyond the piece itself. A store maps references to pieces and may lack any of them. The kind of reference is a parameter, as the operation table is; the kernel does not say how a reference is made. A lazy machine runs a partial state: when a step has to look at a reference it fetches that one piece, and when the store lacks it the run pauses, holding the reference it needs. A pause is not an outcome, and a program cannot observe it. It is proved, for every table and every kind of reference, that cutting a state into pieces loses nothing, that the lazy machine halts with what the plain machine halts with, that more pieces change nothing, and that a waiting run of the request driver can be kept and continued from its root. These theorems do not say how a reference is made. The `Wire` library makes one: a reference is the Blake3 hash of the piece's bytes (see Byte form). `Surface.Keep` runs one turn against a store it is handed piece by piece: when a step needs a piece it does not hold it stops and names it, checks the bytes it is given against that name, and when the turn ends in a request saves the waiting program and reports its root. Reading and writing the files is the host's: `host/out/keep` keeps each piece as one file in a directory, named by the kernel. The session is tested, not proved; each machine run in it is a turn the store theorems cover. The network and attestation are outside the kernel. The definitions are in `kernel/Reflect/Store.lean` and `kernel/Reflect/StoreProof.lean`, the exact statements in `kernel/StoreContract.lean`, and `kernel/StoreCheck.lean` cuts and continues real runs. `host/check.sh` runs `StoreContract.lean`, `StoreCheck.lean` and `KeepCheck.lean`, and the keep command against `examples/keep.hom`. The statements are in `openspec/specs/state-store/spec.md`.

## Byte form

A data value has one byte form, in the part of dCBOR that `Data` has: numbers, arrays, text and names. A number below 2^64 is a CBOR unsigned integer in its shortest form, a larger number is CBOR tag 2 over its bytes, an array is a definite-length CBOR array, a text is a definite-length CBOR text string of UTF-8, and a name is CBOR tag 39 over its number in the number's form. Using tag 2 for large numbers and tag 39 for names, and not normalising text (dCBOR asks for NFC), are this project's rules, not dCBOR's. Text and names came with `add-data-kinds`; the byte form of a number, an array, a reference, and of a program with no string literal did not change. The reader is strict: it refuses every spelling but the writer's. A program's bytes are the bytes of its quoted form, `reify`. A machine value is `[0, d]` for data and `[1, body, captured]` for a function, where `body` is the program its code was compiled from, so a waiting program has a byte form too. A function whose code is not exactly the compilation of a program has no byte form. The byte form lives in its own library, `Wire`, beside `Reflect` and `Surface`; nothing in `Reflect` mentions bytes. By decision D7 of the vision the wire format is tested, not proved: `kernel/WireCheck.lean` checks the RFC 8949 appendix A examples, refused spellings, every string of one or two bytes, and programs and a waiting run kept as bytes. One statement is proved, `Reflect.unreify_reify` in `kernel/Reflect/Syntax.lean`: reading a program's data form gives the program. A piece of stored state has a byte form: a number is itself, a text is the text, a name is the name, an empty list is `[]`, a pair is `[0, head, tail]`, a function is `[1, body, captured]`, and a reference is a 32-byte CBOR byte string. Reading data still refuses a byte string. A reference is the Blake3 hash of a piece's bytes, and Blake3 is a Lean definition, `Wire.Blake3.hash`. Saving cuts a value from the leaves up and stores each part whose bytes pass 256 under its hash (`kernel/Wire/Piece.lean`). A text is not cut: it is stored whole, as one piece, when its byte form passes the size, and kept in place otherwise. A state kept before text and names were data is not migrated: it still reads, and a number in it that was a channel name is now a plain number. The hash, the byte form of a piece and saving are tested, not proved: `kernel/KeepCheck.lean` checks the 22 official Blake3 vectors and saves and continues real runs. That two pieces do not share a hash is assumed (D5). The statements are in `openspec/specs/wire-bytes/spec.md`.

## Surface

`Surface`, the package's third library, holds the reader, from program text with names and indentation to `Reflect` terms, and the renderer, from outcomes to plain text. The reader takes `"..."` as the literal of a text, UTF-8 and on one line, and `'c'` as the number of one ASCII character, so that it can be compared with the head `case` gives of a text. A string is a text, not the array of its code points: equality and the byte form tell the two apart, and `case` takes them apart alike. `text` and `codes` are built-in names of one argument. The renderer writes a text in double quotes with `\n`, `\t`, `\\` and `\"` as escapes, which reads back, and a name as `#n`, which the reader refuses. With `--text` a result that is a text is written raw (`renderMOutcomeText`), and an array is no longer taken for text (`add-data-kinds`; `add-string-literals` had made a string the array of its code points). The `def`s of one block with no `let` between them are a run, and a definition of a run can name a later one: a name that is bound nowhere else and that a later `def` of the run defines is that definition, so a name already bound keeps its meaning and an old program reads to the same term. The reader binds each definition after what it mentions, and reads definitions that mention one another in a ring as `recur` applied to one function of a number that chooses the member. A `case` arm can name an array of a fixed length, `[a, b, c]`, or of a least length, `[a, b, ...rest]`, read as nested `dcase`; an array no arm takes goes to the catch-all arm or is `wrong`, and a catch-all arm that no branch falls to is not read, as before. Neither adds a term or an operation. The reader and the renderer are tested against examples. They are not proved. What runs is the term the reader produced, on the proved machine. The statements are in `openspec/specs/surface-syntax/spec.md`.

## Boundary

The proof boundary is the call from the Zig host into the Lean kernel. The `lean-c-abi` spike (`docs/spikes/lean-c-abi/finding.md`, Lean 4.35.0, Zig 0.16.0) returned `71` from one unboxed exported function to a Zig host that does not contain the formula. The spike shows the call is feasible. The object link and the runtime initializer are in `host/`. Zig passes program text to `reflect_run`, a program and an answers text to `reflect_converse`, a program's byte form to `reflect_run_bytes`, or a program in either form to `reflect_interp`, which runs it through a number of levels of the closed interpreter term `interp` on the machine and reads the answer back, and prints the text it returns. These four, `reflect_keep_start`, `reflect_keep_answer`, `reflect_keep_give`, `reflect_channels`, `reflect_vm_start`, `reflect_vm_from`, `reflect_node_start`, `reflect_node_from` and `reflect_reply_bytes` are the only exports that evaluate; Zig reads nothing and evaluates nothing. A fourth export, `reflect_source_bytes`, gives a program's byte form from its source and evaluates nothing; Zig does not make or inspect the bytes. The `reflect_keep_*` exports run one turn against a store; Zig reads and writes the piece files the kernel names, and does not read, hash or name a piece. The command `host/out/run [--bytes] [--interp[=levels]] [--text] <program-file> [step-budget]` does the same for a program file, through the interpreter with `--interp` and writing a result that is a text raw with `--text`, `host/out/ask <program-file> <answers-file> [step-budget]` runs a program file against an answers file, `host/out/bytes <program-file>` writes a program's byte form to standard output, and `host/out/keep <store-dir> start <program-file>` or `host/out/keep <store-dir> answer <root> <answer-file>` runs one turn with the program's state kept in a directory, and `host/out/chan <program-file> [schedule-file | -] [step-budget] [event-limit]` runs a program as processes over channels and prints the schedule it went through. The host requirements are `openspec/specs/zig-host/spec.md`. The theorems are the source of record in `openspec/specs/code-as-data/spec.md` and `openspec/specs/bytecode-machine/spec.md`.

## Image

The same Lean objects also run with no operating system under them. `unikernel/out/reflect.elf` is one static x86_64 ELF file that Cloud Hypervisor starts by direct kernel boot through the PVH entry: no firmware, no disk, no guest operating system. `unikernel/boot.S` maps the first 4 GiB one-to-one, enters 64-bit mode, enables x87/SSE and optional AVX with XSAVE, and holds the `syscall` entry and the fault stubs. `unikernel/kernel.zig` answers the serial port, memory, random bytes from `RDRAND`, power off, and the system calls musl and the Lean runtime make; musl is Zig's, linked as it is, and reaches the layer with the `syscall` instruction as it would reach Linux. `unikernel/main.zig` initialises the kernel package, passes the source built into the image to `reflect_run`, writes the answer to the serial port and powers off. One processor, one thread, no interrupts, no timer; Lean's event loop is not started (`initialize_libuv` resolves to an empty function). A system call the layer does not answer and a processor fault are reported on the serial port, not survived; contiguous stack growth into the 2 MiB unmapped guard faults on an alternate stack. `unikernel/build.sh` builds on Linux x86_64 with Lean 4.35.0, Zig 0.16.0 and musl 1.2.5, links identical Lean objects into the image and a Linux comparison process, `unikernel/out/reflect-linux`, and records versions, source and object hashes; changed inputs reject reuse. `unikernel/check.sh` boots the image on Cloud Hypervisor 54.0 and compares the whole serial stream with the Linux process. The image has not been rebuilt or checked since `Data` gained text and names (`homoiconic-q59.40`). The image adds the boot code, the layer, musl and Cloud Hypervisor to what is trusted and removes a guest operating system from it. The statements are in `openspec/specs/unikernel-image/spec.md`. The image was rebuilt and checked on morphie on 2026-11-19, after `Data` gained text and names. Given a program's byte form at boot (`--initramfs`), the layer moves the bytes above the image before the stack and allocators are laid out and serves them as the read-only file `/boot/program`; `main.zig` then calls `reflect_interp` on them with the byte-form flag, with the budget and levels from the PVH command line, so one image file runs any program, one per boot, without a rebuild. The layer bounds the bytes (16 MiB, one module) and does not read them; whether they are a program is the kernel's answer.

## Network image

A second image, `unikernel/out/reflect-net.elf` (`unikernel/build-net.sh`), keeps one guest up and answers programs sent over UDP. The layer adds a polling modern virtio-net PCI driver (`unikernel/net.zig`): it maps the device's BARs before touching them, negotiates exactly VERSION_1 and MAC, and runs split RX/TX queues, with Ethernet, ARP, IPv4 and UDP above them and no interrupts. The address and port come from the PVH command line (`reflect.ip`, `reflect.port`). Each datagram carries a 24-byte `RFL1` frame: kind, transport status, correlation number and step budget, then the program's byte form. Zig checks the frame and drops what is malformed before anything is evaluated; it passes the program bytes and budget to `reflect_reply_bytes`, and Lean decodes, runs the machine and writes the bounded-run reply (`Wire.runReplyBytes`, `kernel/Wire/Reply.lean`). Zig never reads a program or an outcome. Requests are served one at a time; a Lean abort or fault during one powers the guest off, and readiness is not claimed again in that boot. `unikernel/check-net.sh` boots it on Cloud Hypervisor 54.0 with a TAP and compares each reply with the same export in a Linux process (`unikernel/out/reply`). With `reflect.quic_port` the guest also serves one `RFL1` exchange per connection over QUIC v1 (`unikernel/quic.zig`: TLS 1.3, AES-128-GCM, X25519, a P-256 certificate), one connection at a time, with its time read from the KVM paravirtual clock; the Lean side is unchanged. The host client pins the SHA-256 of the certificate compiled into the image, so the pin names the source tree's key, not one guest (`homoiconic-q59.49`). The device driver, the stack, the frame and QUIC are trusted, not proved. The statements are in `openspec/specs/unikernel-net/spec.md`.

## Why

- **Lean owns semantics.** A model beside a Zig or Rust interpreter can drift. With `eval` in Lean, the program and the proof are the same artifact, and Lean 4 compiles, so the kernel can run.
- **Zig is the host.** The process needs explicit allocation, files, and a small binary. The host does not duplicate semantics.
- **Rust is out.** The borrow checker is real but is not a Lean theorem. Keeping Rust would add a third compiler to every semantics change. A translator carrying Rust into Lean would make Rust the source of the evaluator, which reverses the decision that Lean is the semantics.

- `add-interpreted-run`: folded. `reflect_interp` and `host/out/run --interp[=levels]` run a program through the metacircular interpreter on the machine and read the answer back; the read-back is tested, not proved. The requirement is in `openspec/specs/zig-host/spec.md`.
- `add-string-literals`: folded. String and character literals in the reader, a string being the array of its code points with `Data` unchanged; `host/out/run --text`; `reflect_interp` takes `flags`. The requirements are additions in `openspec/specs/surface-syntax/spec.md` and `openspec/specs/zig-host/spec.md`. `add-data-kinds` made a string a text.
- `add-def-rings-and-array-patterns`: folded. The definitions of a run name one another, a ring read as `recur` over a function of a member number, and `case` arms that name an array of a fixed or a least length; the reader only, tested, not proved. Functions kept in arrays is left to the owner (`homoiconic-q59.39`). The requirements are in `openspec/specs/surface-syntax/spec.md`.
- `add-data-kinds`: folded. Text and channel names are kinds of data, `Data.text` and `Data.name`, seen by `case` as a list and as a number; `interp` unchanged and its theorems proved again with unchanged statements; `text` and `codes` in the first table; a channel is handed over only as a name value, a number hands over nothing, and a name is held once (`Network.held_nodup`); CBOR text strings and tag 39 on the wire; a text is one piece; `"..."` is a text and `--text` writes a text raw. Kept states made before it are not migrated. The requirements are in `openspec/specs/code-as-data/spec.md`, `openspec/specs/channels/spec.md`, `openspec/specs/wire-bytes/spec.md`, `openspec/specs/state-store/spec.md`, `openspec/specs/surface-syntax/spec.md`, `openspec/specs/bytecode-machine/spec.md` and `openspec/specs/zig-host/spec.md`; the change is `openspec/changes/archive/2026-11-17-add-data-kinds/`.
- `add-unikernel-net`: folded. A second image that serves program bytes over UDP on virtio-net, the `RFL1` frame, `reflect_reply_bytes` and the bounded-run reply form in `Wire.Reply`; `unikernel/build-net.sh` and `unikernel/check-net.sh`. The requirements are in `openspec/specs/unikernel-net/spec.md`, with additions in `openspec/specs/wire-bytes/spec.md` and `openspec/specs/zig-host/spec.md`; the change is `openspec/changes/archive/2026-11-22-add-unikernel-net/`.
- `add-boot-program-bytes`: folded. One image runs a program's byte form given at boot with `--initramfs`, served as `/boot/program` and run through `reflect_interp`; `unikernel/out/reply source`. The requirements are in `openspec/specs/unikernel-image/spec.md`; the change is `openspec/changes/archive/2026-11-22-add-boot-program-bytes/`. Its advise read by another model family is still owed.
- `add-unikernel-quic`: folded. One authenticated QUIC stream on `reflect.quic_port`, the KVM paravirtual clock, the certificate pin, `unikernel/check-quic.sh`. The requirements are in `openspec/specs/unikernel-net/spec.md`; the change is `openspec/changes/archive/2026-11-23-add-unikernel-quic/`.
- `add-network-channels`: folded. A closure and a reply name cross between two guests on `reflect.wire_port` and `reflect.peer`; the `reflect_remote_*` exports; `unikernel/check-wire.sh`. The requirements are in `openspec/specs/channels/spec.md`, `openspec/specs/unikernel-net/spec.md` and `openspec/specs/zig-host/spec.md`; the change is `openspec/changes/archive/2026-11-23-add-network-channels/`.

The partition is the landed artifact those changes cite. This kernel does not add a Zig host or a C ABI. The host landing is the call above.
