## Partition

| Language | Role | Contains an evaluator? |
|---|---|---|
| Lean 4 | The only semantics language. The evaluator, `Reflect`, is Lean 4 source, and the proofs talk about that source. | Yes. This is the only one. |
| Zig | The host: the operating-system process. It handles files, allocation, and the REPL. It loads the Lean runtime and returns the kernel's result. In the machine image it is also the layer that stands where an operating system would. | **No.** It never re-states the semantics or grows a second `eval`. |
| Rust | Absent. It is not a language of the first system. | n/a |

## Circularity

Circularity means the interpreter theorem. An interpreter is a term of the language. For every program, evaluating that term on the program as data equals evaluating the program directly. The theorem is `reflective`, proved about `Reflect`, the evaluator that runs, with no fragment. Its statement is in `openspec/specs/code-as-data/spec.md`.

The first kernel, `Circular` (`add-lean-circular-kernel`), proved the theorem for quote-free programs at one level; `retire-circular-kernel` deleted it, and it is in git at `8b23867` and earlier.

## Reflect

The kernel package holds three Lean libraries, `Reflect`, `Wire` and `Surface`. `Reflect` is the language, its one evaluator, and its proofs. In `Reflect` a program is a data value: data is natural numbers and arrays, and quoting a program is a literal of its data form. The interpreter is one closed term that takes a program as data, and the interpreter theorem holds for every term, with no fragment. A stack machine runs the same language one step at a time, and it is proved equal to direct evaluation. The statements are in `openspec/specs/code-as-data/spec.md` and `openspec/specs/bytecode-machine/spec.md`.

`prim c x` runs an operation from a table, `Ops`: one total function from an operation number and a data value to a data value. Evaluation, the interpreter theorems and the machine theorems are stated for every table. The interpreter is the same term for every table, so a new set of operations is added to a table with no new proof. The first table is exact arithmetic (`kernel/Reflect/Arith.lean`), and the host runs with it (`add-operation-tables`).

## Requests

A program can ask the outside for something and continue from the answer. A request is an ordinary value: `ask payload next` builds a function that hands its payload and the rest of the program to its caller. Nothing is added to the language, evaluation, the interpreter or the machine. A driver outside the program runs it against a list of answers: every function a turn ends in is read as a request, its payload must be data, and the rest of the program runs on the next answer. The driver is defined once, over any way of evaluating, and it is proved that a run is fixed by the program and the answers, and that direct evaluation, the interpreter on data and the machine make the same requests and end the same way. A request carries no mark, so a driven program cannot finish with a function. What a payload means is not part of this. The statements are in `openspec/specs/requests/spec.md`.

## Channels

Several programs can run side by side as processes in one machine and talk over channels. Nothing is added to the language: a process is a program that makes requests, and four shapes of payload are channel requests. `[0]` makes a channel and is answered with its name, a number. `[1, name, message]` sends, `[2, name]` receives, and `[3, program, start]` starts a quoted program on the data `start` as a new process. Every other payload is a request to the outside. A send and a receive meet in one event; there is no queue. A schedule is a list of events, and the new names and the answers from outside are events, so the schedule is the whole record of a run. A process holds the names it made, the names its starter held that occur in its start data, and the names a sender held that occur in a message it received, and it can send or receive only on a name it holds. It is proved, for every table, that a program and a schedule lead to at most one configuration (`network_deterministic`), that a process uses only names it holds and every held name was made by an event of the schedule, that the machine runs a schedule as direct evaluation does, and that what the executable scheduler reports is a run of the program. Holding is kept by the scheduler. A name is a number and can be written by any process; it is not yet a key. The interpreter on data is not covered, and a set of processes cannot be kept on disk. The command `host/out/chan` runs a program as the first process and prints the schedule it went through; given that schedule back, it runs the same events. The definitions are in `kernel/Reflect/Channel.lean` and `kernel/Reflect/ChannelProof.lean`, the exact statements in `kernel/ChannelContract.lean`, and the requirements in `openspec/specs/channels/spec.md`.

## The log

A VM is a program that makes requests, together with the identifiers of the log entries it has acted on. A log is a list of entries, each an identifier and an answer. Handling an entry answers the request the VM is waiting on and records the identifier; an entry whose identifier the VM has acted on changes nothing, and neither does any entry once the program has finished. The state of a VM is the fold of handling over its log, so the log is the record and the state can be made again from it. It is proved, for every table, that a program and a log lead to at most one state, that the state after a log is the state after a prefix carried on through the rest, that an entry already in the log changes nothing, that a state reached by a first part of the log and then given the whole log reaches what the whole log reaches from the start, that the run is the request driver's on the answers of the first deliveries, and that the machine and the executable fold agree with direct evaluation. An identifier is data, and where it comes from is the host's: it is not a hash here and nothing is signed. An entry does not say which request it answers, so the order of first deliveries decides the state. `Surface.Keep` handles a log against a store and saves the state under one root; `host/out/vm` starts a program on a log or hands a log to a kept state. That a restarted state has the root a replay from the start has is tested, not proved. The definitions are in `kernel/Reflect/Log.lean` and `kernel/Reflect/LogProof.lean`, the exact statements in `kernel/LogContract.lean`, and the requirements in `openspec/specs/event-log/spec.md`.

## Nodes

A node joins the two: several processes whose schedule is a log. An op is an event of the scheduler with an identifier, and a node is a configuration of processes together with the identifiers of the ops it has acted on. Applying an op the node has acted on changes nothing; otherwise the event happens as for a schedule. An op whose event cannot happen has no next node, because a log is the record of what happened. It is proved, for every table, that a program and a log lead to at most one node, that an op already in the log changes nothing, that a node reached by a first part of the log and given the whole log reaches what the whole log reaches from the start, that a node's processes are where the schedule of first deliveries leads (so the channel theorems hold of them), and that the machine and the executable `nodeRun` agree with direct evaluation. An event is also split into the machine runs it needs and the configuration once they end (`plan`), and that split is proved to be the event, both ways. `Surface.Keep` applies a log to processes against a store using `plan`, and saves the node under one root; `host/out/node` starts a program on a log or applies a log to a kept node. The session, and that a restarted node has the root a replay has, are tested, not proved. The definitions are in `kernel/Reflect/Node.lean` and `kernel/Reflect/NodeProof.lean`, the exact statements in `kernel/NodeContract.lean`, and the requirements in `openspec/specs/logged-processes/spec.md`.

## Stored state

A running program's state can be held in pieces. A piece is a number, an empty list, a pair, a function, or a reference to another piece, and one type serves for data, values and environments. A store maps references to pieces and may lack any of them. The kind of reference is a parameter, as the operation table is; the kernel does not say how a reference is made. A lazy machine runs a partial state: when a step has to look at a reference it fetches that one piece, and when the store lacks it the run pauses, holding the reference it needs. A pause is not an outcome, and a program cannot observe it. It is proved, for every table and every kind of reference, that cutting a state into pieces loses nothing, that the lazy machine halts with what the plain machine halts with, that more pieces change nothing, and that a waiting run of the request driver can be kept and continued from its root. These theorems do not say how a reference is made. The `Wire` library makes one: a reference is the Blake3 hash of the piece's bytes (see Byte form). `Surface.Keep` runs one turn against a store it is handed piece by piece: when a step needs a piece it does not hold it stops and names it, checks the bytes it is given against that name, and when the turn ends in a request saves the waiting program and reports its root. Reading and writing the files is the host's: `host/out/keep` keeps each piece as one file in a directory, named by the kernel. The session is tested, not proved; each machine run in it is a turn the store theorems cover. The network and attestation are outside the kernel. The definitions are in `kernel/Reflect/Store.lean` and `kernel/Reflect/StoreProof.lean`, the exact statements in `kernel/StoreContract.lean`, and `kernel/StoreCheck.lean` cuts and continues real runs. `host/check.sh` runs `StoreContract.lean`, `StoreCheck.lean` and `KeepCheck.lean`, and the keep command against `examples/keep.hom`. The statements are in `openspec/specs/state-store/spec.md`.

## Byte form

A data value has one byte form, in the part of dCBOR that `Data` has: numbers and arrays. A number below 2^64 is a CBOR unsigned integer in its shortest form, a larger number is CBOR tag 2 over its bytes, and an array is a definite-length CBOR array. Using tag 2 for large numbers is this project's rule; dCBOR does not define it. The reader is strict: it refuses every spelling but the writer's. A program's bytes are the bytes of its quoted form, `reify`. A machine value is `[0, d]` for data and `[1, body, captured]` for a function, where `body` is the program its code was compiled from, so a waiting program has a byte form too. A function whose code is not exactly the compilation of a program has no byte form. The byte form lives in its own library, `Wire`, beside `Reflect` and `Surface`; nothing in `Reflect` mentions bytes. By decision D7 of the vision the wire format is tested, not proved: `kernel/WireCheck.lean` checks the RFC 8949 appendix A examples, refused spellings, every string of one or two bytes, and programs and a waiting run kept as bytes. One statement is proved, `Reflect.unreify_reify` in `kernel/Reflect/Syntax.lean`: reading a program's data form gives the program. A piece of stored state has a byte form: a number is itself, an empty list is `[]`, a pair is `[0, head, tail]`, a function is `[1, body, captured]`, and a reference is a 32-byte CBOR byte string. Reading data still refuses a byte string. A reference is the Blake3 hash of a piece's bytes, and Blake3 is a Lean definition, `Wire.Blake3.hash`. Saving cuts a value from the leaves up and stores each part whose bytes pass 256 under its hash (`kernel/Wire/Piece.lean`). The hash, the byte form of a piece and saving are tested, not proved: `kernel/KeepCheck.lean` checks the 22 official Blake3 vectors and saves and continues real runs. That two pieces do not share a hash is assumed (D5). The statements are in `openspec/specs/wire-bytes/spec.md`.

## Surface

`Surface`, the package's third library, holds the reader, from program text with names and indentation to `Reflect` terms, and the renderer, from outcomes to plain text. The reader takes `"..."` as the array of the text's code points, UTF-8 and on one line, and `'c'` as the number of one ASCII character. `Data` is unchanged: a string is the array of its code points, and nothing in a program or on the wire tells the two apart. The renderer can write a result that is an array of the code points of printable characters, tabs and line feeds as the text it spells (`renderMOutcomeText`); without that request a string prints as numbers. The reader and the renderer are tested against examples. They are not proved. What runs is the term the reader produced, on the proved machine. The statements are in `openspec/specs/surface-syntax/spec.md`.

## Boundary

The proof boundary is the call from the Zig host into the Lean kernel. The `lean-c-abi` spike (`docs/spikes/lean-c-abi/finding.md`, Lean 4.35.0, Zig 0.16.0) returned `71` from one unboxed exported function to a Zig host that does not contain the formula. The spike shows the call is feasible. The object link and the runtime initializer are in `host/`. Zig passes program text to `reflect_run`, a program and an answers text to `reflect_converse`, a program's byte form to `reflect_run_bytes`, or a program in either form to `reflect_interp`, which runs it through a number of levels of the closed interpreter term `interp` on the machine and reads the answer back, and prints the text it returns. These four, `reflect_keep_start`, `reflect_keep_answer`, `reflect_keep_give`, `reflect_channels`, `reflect_vm_start`, `reflect_vm_from`, `reflect_node_start` and `reflect_node_from` are the only exports that evaluate; Zig reads nothing and evaluates nothing. A fourth export, `reflect_source_bytes`, gives a program's byte form from its source and evaluates nothing; Zig does not make or inspect the bytes. The `reflect_keep_*` exports run one turn against a store; Zig reads and writes the piece files the kernel names, and does not read, hash or name a piece. The command `host/out/run [--bytes] [--interp[=levels]] [--text] <program-file> [step-budget]` does the same for a program file, through the interpreter with `--interp` and writing a result of printable code points as text with `--text`, `host/out/ask <program-file> <answers-file> [step-budget]` runs a program file against an answers file, `host/out/bytes <program-file>` writes a program's byte form to standard output, and `host/out/keep <store-dir> start <program-file>` or `host/out/keep <store-dir> answer <root> <answer-file>` runs one turn with the program's state kept in a directory, and `host/out/chan <program-file> [schedule-file | -] [step-budget] [event-limit]` runs a program as processes over channels and prints the schedule it went through. The host requirements are `openspec/specs/zig-host/spec.md`. The theorems are the source of record in `openspec/specs/code-as-data/spec.md` and `openspec/specs/bytecode-machine/spec.md`.

## Image

The same Lean objects also run with no operating system under them. `unikernel/out/reflect.elf` is one static x86_64 ELF file that Cloud Hypervisor starts by direct kernel boot through the PVH entry: no firmware, no disk, no guest operating system. `unikernel/boot.S` maps the first 4 GiB one-to-one, enters 64-bit mode, enables x87/SSE and optional AVX with XSAVE, and holds the `syscall` entry and the fault stubs. `unikernel/kernel.zig` answers the serial port, memory, random bytes from `RDRAND`, power off, and the system calls musl and the Lean runtime make; musl is Zig's, linked as it is, and reaches the layer with the `syscall` instruction as it would reach Linux. `unikernel/main.zig` initialises the kernel package, passes the source built into the image to `reflect_run`, writes the answer to the serial port and powers off. One processor, one thread, no interrupts, no timer; Lean's event loop is not started (`initialize_libuv` resolves to an empty function). A system call the layer does not answer and a processor fault are reported on the serial port, not survived; contiguous stack growth into the 2 MiB unmapped guard faults on an alternate stack. `unikernel/build.sh` builds on Linux x86_64 with Lean 4.35.0, Zig 0.16.0 and musl 1.2.5, links identical Lean objects into the image and a Linux comparison process, `unikernel/out/reflect-linux`, and records versions, source and object hashes; changed inputs reject reuse. `unikernel/check.sh` boots the image on Cloud Hypervisor 54.0 and compares the whole serial stream with the Linux process. The image adds the boot code, the layer, musl and Cloud Hypervisor to what is trusted and removes a guest operating system from it. The statements are in `openspec/specs/unikernel-image/spec.md`.

## Why

- **Lean owns semantics.** A model beside a Zig or Rust interpreter can drift. With `eval` in Lean, the program and the proof are the same artifact, and Lean 4 compiles, so the kernel can run.
- **Zig is the host.** The process needs explicit allocation, files, and a small binary. The host does not duplicate semantics.
- **Rust is out.** The borrow checker is real but is not a Lean theorem. Keeping Rust would add a third compiler to every semantics change. A translator carrying Rust into Lean would make Rust the source of the evaluator, which reverses the decision that Lean is the semantics.
