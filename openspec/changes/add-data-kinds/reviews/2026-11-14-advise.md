## Found

### Interpreter and evaluation

The twelve new rules in section 2 agree with `B.evalBody` in `Interpreter.lean`. I found no missing new constructor-specific `Direct` rule or corresponding `evalFuel` branch beyond those twelve. In particular:

- `succName` and `succText`: successor first rejects a closure by its value tag, then cases on the payload. Names enter a numeric arm and its own `succ` produces a plain number; text enters a list arm and returns `W`, the data `[2]`.
- `consTailName` and `consText`: construction evaluates the head, rejects a head closure before evaluating the tail, then checks the tail's value tag and cases on its payload. A name returns `W`; either text shape enters `built`, whose own `cons` makes the specified array. It uses the original text payload, not the head/tail bound by that test.
- `caseNameZero`, `caseNameSucc`, `caseTextNil`, `caseTextCons`: analysis invokes precisely the branch selected by the new host `dcase`. Its constructed environment contains the plain predecessor for a name, or text tail at index 0 and numeric code point at index 1 for nonempty text. No conversion loses the new kind.
- `primCodeText`: the operation branch returns `W` before evaluating the argument. The three name-operation rules enter `argument`; errors pass through `bind`, argument closures return `W`, and data arguments are passed intact to its own `prim` with the name still the code value.

### Holding and logged processes

The sieve leak is closed. The quoted filter contains numeric tags, indices and literals, but no name literals; scanning `[code, out, report]` therefore grants only the actual name values in `out` and `report`. Numeric candidates, including 0 and numbers coinciding with issued channels, grant nothing. The child that still needs the original numbers channel is process 2; later filters get their own input and report channels.

An actual name inside quoted data is different: `reify (.lit (.name n))` is `[2, #n]`. If that quoted form occurs in start data or in a message, the recursive array scan finds it and transfers holding when the sender/starter holds it. This is intentional structural transfer, not a code-opacity guarantee. A name spliced solely into the separate spawn-program field does not transfer holding. Similarly, `[[[2, #n]]]` in a message transfers `n`; `[[[2, n]]]` does not. Possession of a value alone never satisfies the held-list checks.

`gain` preserves uniqueness assuming both its inputs are unique; it does not deduplicate arbitrary `handed` lists. The proposed invariant supplies the needed assumption because `grant` filters a unique sender list. Freshness additionally needs held names to lie in `cfg.names`; the design correctly identifies that stronger invariant. The theorem applies to `Network` runs from `Begin`, not arbitrary imported configurations. Kept nodes are already trusted for their held lists.

Numeric `[1, n, m]` and `[2, n]` become outside requests. Outside answers do not change holding. They can affect computation, as outside answers always can, but do not authorize channel communication. This behavioral choice is explicit.

`Node.plan` must change its fresh job to `.turn c (.name n)` and its communication result to use `gain`, as specified. `Event.fresh` fields, event tags, process indices, held-list storage, node names, and unbound indices should remain numbers. Log identifiers and answers already use `Data`; `Log.decEq` needs both new constructors, not a wholesale conversion of identifiers into names. I found no additional numeric field that must become a name. Add a logged-node regression exercising fresh, transfer, duplicate delivery, save and restart: the existing contracts do not test the session's bytes.

### Bytes

The proposed encodings are disjoint: major type 3 text, tag 39 names, tag 2 large naturals, and bare major type 2 references in pieces. Parsing the byte string under tag 2 inside the numeric branch avoids confusing a 32-byte bignum magnitude with a reference. A name at or above `2^64` is tag 39 around tag 2 around the canonical magnitude bytes; at exactly `2^64`, that magnitude has nine bytes. Nested tag 39 must be refused, as must tag 2 encoding a small number, long-form tag heads, and nonminimal inner numbers.

The [IANA registry](https://www.iana.org/assignments/cbor-tags/cbor-tags.xhtml) assigns 39 to Identifier, and its [referenced specification](https://github.com/lucas-clemente/cbor-specs/blob/master/id.md) explicitly permits numeric identifiers. This use is compatible; it is not a private tag allocation. Skipping NFC is stated honestly as a departure from dCBOR. With scalar-valued characters and strict UTF-8 decoding, distinct character sequences have distinct UTF-8 forms even without normalization. This remains tested, not proved.

The size-domain wording should also explicitly bound the magnitude-byte length of a name's underlying natural, just as it bounds a plain natural. The existing physical-size limitation is sensible, but wrapping a natural in `name` does not remove it.

### Section 6 decisions

1. **List Char: right.** It avoids quadratic tail copying and follows the deferred-representation policy. It does not solve the bead's memory complaint; the amendment admits that.
2. **Name seen as number: right.** It satisfies the fixed-interpreter discipline without arithmetic manufacturing name values.
3. **Only start data grants names: owner's choice.** Coherent, and explicitly tested by the proposed guess example; names nested in quoted *start data* still grant.
4. **Delete printable-array `--text`: owner's choice.** Clear semantics, with deliberate compatibility impact.
5. **Tag 39: right.** Its registered semantics support this use.
6. **No normalization: owner's choice.** Honest if claims remain about this project's canonical bytes rather than dCBOR compliance.
7. **Numeric receive is outside: owner's choice.** Consistent with the generic fallback rule and distinct from an unauthorized typed receive.
8. **No kind operation: owner's choice.** Existing operations already distinguish some kinds; see Required 3.
9. **Prove held_nodup: right.** The fallback is an explicit scope reduction, not fulfillment of the present proved SHALL; if exercised, revise the requirement and contract task before claiming completion.
10. **No kept-state migration: owner's choice.** Old nodes can still be structurally readable, but their numeric payloads now classify differently. Do not imply that all old roots will be rejected or converted.
