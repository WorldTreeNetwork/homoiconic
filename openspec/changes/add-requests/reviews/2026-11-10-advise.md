Review of the definitions and proofs

`source`, `interpreted` and `machine` are honest instances (`kernel/Reflect/Request.lean:72–104`). In particular, interpreted evaluation is `Direct []` of the actual object-language `evalTerm` applied to reified syntax and an encoded environment. It does not define evaluation by asserting the source result. `InteractI` initially runs `interp` on reified program data and subsequently uses that interpreted instance for both selector evaluations (`:110–113`). `InteractM` initially runs compiled code, and its subsequent evaluations quantify actual finite machine runs (`:95–104,115–117`). The host-level classification of encoded results is explicit; interpreting the driver itself is not claimed.

The simulation's equivalence premise is proved, rather than assumed as an axiom: interpreter coverage and forward interpretation establish `sim_interpreted.eval` (`RequestProof.lean:212–243`), and forward/reverse machine results establish `sim_machine.eval` (`:245–295`). `Sim.drive` then transports whole derivations (`:112–189`). There is no source-evaluation escape hatch in either compared definition.

I found no vacuous instance or unreachable-rule trick. The full executable checks exercise stopping, waiting, answering and function-valued-payload rejection. Additional scratch checks exercised failure and divergence during payload evaluation. Scratch Lean examples also constructed an `Interact` derivation for a literal and transported it into actual `InteractI` and `InteractM` derivations for arbitrary `[Ops]`.

For the three concrete instances, the five rules at `Request.lean:56–67` partition terminating cases correctly:

- A nonfunction result stops immediately.
- A function's payload evaluation producing an error stops with that error.
- A function-valued payload stops with `wrong`.
- A data payload with no remaining answers records that payload and waits.
- A data payload with an answer records it, resumes, and continues.

There is no overlap: function and data classifications are disjoint, evaluation is deterministic, and empty/nonempty answer lists distinguish wait from answer. Generic `Sys` alone does not guarantee these properties; `Sys.Det` records the assumptions used by generic determinism (`RequestProof.lean:22–24`), and `source_det` proves them for source evaluation. Arbitrary malformed encoded outcomes are not reachable in `InteractI`, as coverage shows. Divergence in initial evaluation, payload selection or resumption deliberately has no finite ending. Beyond the protocol clarification in required fix 1, the driver prose matches these rules.

The nine signatures in `kernel/RequestContract.lean:11–56` support determinism, extra-answer invariance, interpreter agreement and coverage, machine agreement and coverage, and finished/waiting executable soundness. Resume is a conditional composition theorem: it assumes a terminating resumption and a derivation for the remaining run. It does not assert that every waiting continuation terminates. Together with determinism it gives equality with any completed replay of the extended answers; the pending payload was already recorded, so it is not recorded twice.

Executable fidelity and proof limits
