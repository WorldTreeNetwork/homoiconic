## Blind take — written before opening the design or tasks

1. Pin the boundary: Lean alone reads source, evaluates, and renders; Zig, assembly, and C only transport bytes and supply runtime services.
2. Pin a reproducible static ELF build with explicit Lean, Zig, libc, CPU-feature, and Cloud Hypervisor versions; distinguish spike evidence from the supported target.
3. Pin initialization and the exact exports permitted without libuv, including their transitive initialization, allocation, failure, and shutdown paths.
4. Refuse to infer general runtime compatibility from one factorial boot or from the absence of explicit IO in the evaluator.
5. Pin the syscall ABI: preserve the caller's red zone, required registers and enabled extended state, maintain stack alignment, and make CPU feature assumptions explicit.
6. Refuse an unchecked shared-stack overflow claim: reserve syscall headroom and explain detection and fault reporting when the program stack is exhausted.
7. Pin bounded, nonoverlapping memory regions, honest unsupported-syscall behavior, and explicit treatment of stand-in time and randomness.
8. Pin byte-for-byte output parity for values, exhaustion, malformed input, embedded zero bytes, and answers exceeding the initial output buffer.
9. Pin checks that distinguish guest completion from timeout, boot failure, missing KVM, and stale artifacts, with clean-build evidence.
10. Tradeoff: reusing an unmodified libc reduces replacement code but imports an ABI and startup surface that must be bounded and checked rather than assumed away.

## Comparison and steelman

The author has answered substantial parts of the blind take. Reusing musl is supported by a real boot, not just a proposed port. The design adds merged free ranges, replaces the spike's random stand-in, explicitly reserves a stack guard and an alternate fault stack, and checks the whole serial stream, timeout and hypervisor status. The missing-syscall mutation is a useful negative control. One processor, one built-in program, no interrupts and no return from faults make this a much smaller contract than a general Linux compatibility layer. I would keep those choices.

The strongest argument for accepting now is that the new low-level details can be verified during implementation. The difficulty is that several current acceptance paths would also pass an implementation that violates a stated requirement: short answers hide a fixed-buffer limit, a runtime stack message hides a broken guard/IST path, and a factorial answer says nothing about the absence of another reader. The fixes below specify what the implementation must demonstrate; they do not ask for another architecture or a general-purpose operating system.

## Required contract fixes

### R1 — P1: give the Linux build a successful prerequisite

Locations: `proposal.md:39`, `proposal.md:59`, `design.md:39`; evidence: `docs/spikes/lean-freestanding/repro-command.sh:5` and the finding's “Not shown” section.

The user journey starts with `sh host/check.sh` on Linux, while the cited evidence explicitly says that command fails at its final link with duplicate `_start`. The design requires its objects but says the image build does not compile Lean itself; the proposal also leaves the host script unchanged. The syntax-error scenario then requires a working `host/out/run` oracle. Partial objects left by a failing command are sufficient for a spike, but do not define a successful clean build or provide that Linux oracle.

Required: choose and name a successful Linux object-production path, or make the host-link repair an explicit prerequisite/dependency. Define how the host comparison is obtained. Require a clean-output build with the pinned Linux Lean toolchain, Zig/musl and Cloud Hypervisor version, explicit object provenance, and failure on missing/stale/wrong-platform artifacts. This can be a dependency correction; it need not expand this node into a host repair. Do not bless ignoring `host/check.sh` failures.

### R2 — P1: make the stack safety claim both bounded and observable

Locations: `specs/unikernel-image/spec.md:33`, `specs/unikernel-image/spec.md:41`, `design.md:29`, `design.md:33`.

The guard and IST design is appropriate, but the scenario accepts either a processor report or a runtime report. An early runtime check could therefore pass with the guard still mapped or the TSS/IST broken. A report after corruption would pass too. The scenario does not check the requirement that other memory remains untouched. Also, a guard catches accesses into it; merely moving the stack pointer across it does not fault. Large unprobed allocations can skip a guard, which is precisely the case addressed by [GCC's stack-clash protection](https://gcc.gnu.org/onlinedocs/gcc/Instrumentation-Options.html).

Required: state the supported stack-growth invariant for the linked code, including syscall save-area/dispatcher headroom, guard alignment and exclusion from both allocators. Justify that frames cannot skip the guard, provide probing/checking, or narrow the guarantee explicitly. Keep the deep-source scenario, but add a deterministic guard-crossing check that requires a page-fault report from the alternate stack, checks the fault address and adjacent-memory integrity, and rejects reset/triple fault, timeout and ordinary success. A runtime-only diagnostic must not discharge that hardware check.

The alternate stack is especially necessary here: Lean 4.35's native stack report is installed through `sigaction` and `sigaltstack`, whereas the proposed layer treats signal setup as a fixed-value operation. It does not deliver those Linux signals. The ordinary runtime signal handler cannot be assumed to produce the promised report. See [Lean's pinned stack-overflow implementation](https://raw.githubusercontent.com/leanprover/lean4/v4.35.0/src/runtime/stack_overflow.cpp).

### R3 — P1: pin the syscall/CPU contract and a preservation check

Locations: `proposal.md:22`, `proposal.md:29`; evidence: `docs/spikes/lean-freestanding/src/boot.S:99` and `:135`.

One privilege level is not itself unsound. `SYSCALL` does not switch the stack; software supplies that policy, as documented in [Linux's x86-64 entry source](https://raw.githubusercontent.com/torvalds/linux/master/arch/x86/entry/entry_64.S). The spike skips 128 bytes before pushing, preserves the required general registers, aligns the dispatch stack, and saves/restores extended state. Those are the right obligations. There is no need to introduce a privilege transition.

However, the proposal says it turns on the vector state the processor has without bounding that state or the save area. The spike enables only x87/SSE/optional AVX and reserves 4096 bytes; it also skips XSAVE setup when unsupported but executes `xsave64` unconditionally on a syscall. The current contract neither requires XSAVE support nor defines rejection/fallback. Its three program scenarios cannot check register preservation. [Intel's XSAVE architecture, chapter 13](https://cdrdv2-public.intel.com/782149/253665-sdm-vol-1.pdf) specifies feature detection, XCR0-enabled components, save-area layout and alignment; a fixed area is defensible only for a bounded enabled set.

Required: pin the CPU feature floor or graceful fallback/rejection, enabled state mask, save-area sizing/alignment, red-zone preservation, register/flags return contract and dispatch-stack alignment. Add a syscall probe with sentinel red-zone bytes, general registers, and enabled floating/vector state across a handler that actually clobbers that state. Check unsupported-feature behavior as well. A bounded x87/SSE/AVX policy is enough; enabling every reported extension is not required.

### R4 — P1: require complete output beyond the spike's buffer

Locations: `specs/unikernel-image/spec.md:17`, `design.md:47`; evidence: `docs/spikes/lean-freestanding/src/main.zig:13` and `:26`, `host/run.zig:46`.

The requirement promises the kernel's text for a value without a size restriction. The spike returns 3 when the rendering exceeds 65536 bytes, while the existing host allocates the reported size and retries. All three proposed fixtures fit the spike buffer, so importing that behavior would pass the planned check and violate the requirement. The existing host scenario already supplies a concrete 128894-byte array rendering.

Required: specify handling of the length returned by `reflect_run`, including capacity growth/retry without inspecting the answer, and add a byte-for-byte long-answer scenario exceeding the initial buffer, including its newline and `reflect: exit 0`. Allocation or write failure should be distinguished from a successful kernel answer. This is not a request to promise unlimited memory. A small embedded-zero-byte fixture is also useful to retain the pointer/length boundary already specified by `zig-host`.

### R5 — P2: specify and check the new random-source behavior

Locations: `proposal.md:35`, `specs/unikernel-image/spec.md:49`.

The last requirement has no scenarios. In particular, the spike uses a tick-counter generator; it provides no evidence for either the new RDRAND path or the mandated report when the instruction is absent. Presence of the instruction is also not sufficient: a supported RDRAND invocation can report failure through its carry flag. [Intel's DRNG implementation guide](https://www.intel.com/content/www/us/en/developer/articles/guide/intel-digital-random-number-generator-drng-software-implementation-guide.html) requires checking that flag and describes bounded retries.

Required: define bounded retry and exhaustion behavior, with no clock-based fallback or successful return of invalid random bytes. Add controlled absent-feature and repeated-failure scenarios that require the diagnostic and termination, plus evidence that both startup random bytes and the served random interfaces use successful processor results. The one-thread/no-event-loop and clock-independence clauses also need named evidence: a pinned call-path/source audit and a link/boot check are suitable; a histogram is not a useful test of the random-source requirement.

### R6 — P2: scope the prohibition to a second reader

Location: `specs/unikernel-image/spec.md:7`.

The image “SHALL NOT hold a second evaluator or a reader” literally forbids the Lean reader it must contain to call `reflect_run`. The proposal's “Nothing in the image reads the program” has the same scope problem. The diagram and existing Lean exports make the intended partition clear, and I found no design that evaluates or reads surface syntax in Zig, assembly or C. Parsing ELF metadata, syscall numbers and the `/dev/urandom` path is infrastructure, not a language reader.

Required: say explicitly that Lean owns the image's reader, compiler, evaluator and rendering, and that the non-Lean image code contains no reader or evaluator. Add a source/link inspection scenario for that boundary and the shared Lean object path. Output equality for factorial alone cannot establish it.

## Event-loop assessment

The no-op is defensible for the pinned entry path, with a narrower argument than “Lean does no IO.” At `87afab3`, `reflect_run` copies bytes, calls `Surface.runText`, then copies its rendering. Reading, compilation, machine execution and rendering stay in Lean; no task or asynchronous IO appears in that path. The other three exports at that reference likewise use pure byte/text paths, but this image only needs to promise the one it calls.

Upstream Lean 4.35's [runtime initializer](https://raw.githubusercontent.com/leanprover/lean4/v4.35.0/src/runtime/init_module.cpp) initializes allocation, objects, IO, threading bookkeeping, mutexes, process and stack-overflow support before calling `initialize_libuv`. Its [libuv initializer](https://raw.githubusercontent.com/leanprover/lean4/v4.35.0/src/runtime/libuv.cpp) initializes timer/socket/signal/loop facilities as well as starting the loop thread. Replacing it skips all those facilities, not just thread creation. The pinned [thread initializer](https://raw.githubusercontent.com/leanprover/lean4/v4.35.0/src/runtime/thread.cpp) itself creates bookkeeping, not a worker thread. These facts support the narrow substitution; they do not establish safety for arbitrary future module initializers or exports.

Normal initialization/error reporting can still use synchronous C-library IO; `host/runtime.c` calls `lean_io_result_show_error` on failure. That is not by itself a need for the event loop. Retain the remaining runtime initialization and the existing end-of-initialization call, verify which symbol the link resolves, and re-audit the permitted path when imports or toolchain versions change. R5 asks for this evidence, not for implementing Lean tasks, networking or a scheduler.
