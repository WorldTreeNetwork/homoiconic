### 1. Blocking: a catch-all binder captures names in sibling arms

Location: `kernel/Surface/Read.lean:667`, especially explicit-arm translations at lines 669–675. `base` includes the catch-all's name for every arm, so a name introduced in one pattern is visible in other arms. This silently changes the program and also defeats unbound-name refusal.

Input:

```text
let x = 99
case 0
  0 -> x
  x -> x
```

Returned term:

```text
app (lam
  (app (lam (dcase (var 0) (var 0) (var 1) (var 0) (var 2))) (N 0)))
  (N 99)
```

Actual result: `0`. The explicit zero arm must refer to the outer `x` and return `99`. In this lowering, its body should be `var 1`, not `var 0`.

Input:

```text
case 0
  0 -> ghost
  ghost -> 2
```

Returned term:

```text
app (lam (dcase (var 0) (var 0) (N 2) (N 2) (N 2))) (N 0)
```

Actual result: `0`; required behavior: refuse the unbound `ghost` in the zero arm.

The same problem was run with successor and cons arms. Replacing the first example's case with `case 3 / m + 1 -> x / x -> x` returns the same term with scrutinee `N 3`, and prints `3` instead of `99`. With `case [1] / [h, ...t] -> x / x -> x`, the scrutinee is `cons (N 1) (lit (arr []))`; all other term components are the same, and it prints `[1]` instead of `99`. A `let` inside the explicit arm also inherits the wrong binding.

Owed: preserve the synthetic scrutinee slot without exposing the catch-all name to explicit arms; bind that name only while translating the catch-all body. Add exact-term, result, and unbound-name regression checks for zero, successor, empty, and cons arms, including an arm-local `let`.

### 2. Blocking: successor consumes a dedented statement

Location: `kernel/Surface/Read.lean:340`. `plusLoop` uses `peekRaw` for the required `1`, bypassing the active layout limit.

Input:

```text
let x = 0 +
1
x
```

Returned term:

```text
app (lam (var 0)) (succ (N 0))
```

Actual result: `1`. This must be refused: the `1` is at the enclosing block's column, so it cannot continue the preceding binding. Otherwise the program has an incomplete successor and two value lines. This contradicts the block rule and the explicit layout description in `design.md:132`.

Input:

```text
let x = 0 +
1
  + 1
x
```

Returned term:

```text
app (lam (var 0)) (succ (succ (N 0)))
```

Actual result: `2`; it must likewise be refused. Positive controls with an indented `1`, or a same-line `+ 1`, both read correctly and return `1`.

Owed: respect the active layout limit when consuming the successor operand, audit other raw token reads at continuation boundaries, and add failing-refusal tests plus the positive controls.

## Conclusions from reading, with runtime corroboration where stated

### 3. Blocking contract inconsistency: the numeric-code transition is not scoped

Locations: `openspec/changes/move-host-to-reflect/specs/zig-host/spec.md:8`, `proposal.md:23`, `proposal.md:24`, `design.md:122`, `host/check.zig:83`, and living `openspec/specs/zig-host/spec.md:53`.

The delta says unconditionally that there SHALL NOT be a numeric result code. The design explicitly retains `kernel_run` and its code. The host still initializes Circular, calls `kernel_run`, and prints numeric results; the linked check visibly printed `0`, `1`, and `4294967295`. Thus the proposal's “After this change nothing calls them” and “there is no result code” are false of the built executable. Keeping compatibility until the next change is coherent, but these requirements and claims do not describe that transition.

Also, only the first living zig-host requirement is modified. The unchanged “One evaluator” scenario still requires the outcome to come from `kernel_run`, which contradicts using `reflect_run` as the new evaluation path when folded.

Owed: scope the absence of numeric outcome codes to `reflect_run`, explicitly document retained legacy calls/checks, correct the proposal, and add a delta for the surviving scenario that names `kernel_run`. Alternatively remove legacy use now if that is the intended scope; merely retaining its export is different from continuing to call it. Do not fold mutually inconsistent requirements.

### 4. Scenario coverage is incomplete despite the green suite

Locations: zig-host delta lines 16–20 and 28–32; `kernel/Surface/Expect.lean:149` and `:154`; `kernel/Surface/Check.lean:74`.

The large-index scenario says a term is run and rendered. The check constructs `.unbound 2147483647` directly and calls the source-outcome renderer; it never runs that term or tests `renderState`/`renderMOutcome` for it. The design acknowledges renderer-only coverage at line 139, but this is weaker than the scenario. A direct Lean machine check of `var 2147483647` is possible without permitting unbound names in surface syntax.

The divergence scenario gives a self-applying function applied to itself. The Reflect host cases instead contain only `def loop x = loop x; loop 0`. This tests divergence, but does not exercise that specified surface program. The old Circular self-application check uses a different reader and evaluator.

Owed: add loudly failing checks that compile/run/render the large-index term, distinguish it from an exhausted machine run, and pass the stated self-application surface program through `reflect_run`; or amend the scenarios explicitly to the intended coverage. Add the reader regressions from findings 1 and 2 to the committed suite.

### 5. Completion record names artifacts and behavior that do not exist

Locations: `openspec/changes/move-host-to-reflect/tasks.md:4` and `:8`.

`kernel/Surface/Examples.lean` does not exist; the example specification is `Expect.lean`. The Zig check passes embedded byte slices generated into `out/cases.zig`, not program files. The actual design/proposal correctly excludes a file-running command. The checked reader-refusal task at line 5 also overstates completion in light of finding 1.

Owed: correct the artifact path and input description, and do not record reader refusal as complete until its regression checks pass.
