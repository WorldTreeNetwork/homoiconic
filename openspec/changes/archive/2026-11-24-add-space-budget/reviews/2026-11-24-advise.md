# Advise read, 2026-11-24

Fable, fresh context, read-only: this directory as first written (default 8000000 cells, the answer bounded in cells, no `trail`), `reflect_live_cells` in `kernel/ffi.c`, and the code paths the design names. No Lean for the change existed. The reader ran the harness (`spaceBench live`) and today's `host/out/run` on the Mac; nothing was booted.

**Verdict: SEND-BACK.** The core choice (a proved ledger plus a runtime count asked only when the ledger is spent) holds up, and most theorem statements are true and provable. But the design as written does not meet its own acceptance at the default of 8000000 cells, one theorem is vacuous as specified, and one accepted answer changes sides without being named.

## Blocking findings

1. **An answer that fits still runs the printer out of memory at boot.** Case A's answer is 7000001 cells as a tree, passes `Data.fits d 8000000`, and printing it peaks at 531 MiB (2M items 329 MiB, 1M items 182 MiB, about 157 bytes an item): `renderItems` holds a String and a list cell per item before joining, and `main.zig` runs the program a second time into a buffer of the answer's size. "About ten bytes per cell" is wrong by roughly 8 times, and cost per cell varies with item length (3.5M empty texts: 266 MiB), so a cell count cannot bound the printer. The reply path copies the answer into an `Item` tree first. Smallest fix: give the written answer its own bound, set by measurement; the existing 2 MiB literal checks need about 4.19M cells written, so that bound has a floor.
2. **The memory sum for 8000000 cells is not supported.** Case B peaks at 387 MiB before it is refused. Usable memory is smaller than 512 MiB: the map area is three quarters of what remains after image and stack, about 360 MiB (`unikernel/kernel.zig`). The step's result exists before the charge is tested, for `cons` onto a text and `codes` as well as `prim`. The walk's table is not "12 bytes per cell of the limit": it doubles, up to 32 bytes per counted object after a doubling and 48 while rehashing; case C jumps from 246 to 391 MiB between limits 8M and 10M. "A limit in proportion" is therefore wrong advice. The first ledger period holds the start state plus `cells`.
3. **A documented answer changes sides and the design does not say so.** Case C is the README row "list of zeros, 1 MiB, one interpreter … the answer". Under the scheme it ends out of space at 8M, 10M, 12M and 16M, because the count includes the program held as data and the bar is half the limit; yet the line says `within 8000000 cells`. It is not in `check.sh`, but it contradicts "no existing reply byte changes".
4. **`runSpace_within` is vacuous as specified.** The table charges 2 for "a halt, anything else" and `step` is total, so `madeIn n s ≥ n` and `∀ n, madeIn n s ≤ credit` is never satisfiable. State it as `madeIn fuel s ≤ credit → …`.
5. **`Data.fits`, `Wire.fitsValue` and `Data.cells` can add a stack overflow that is not there today.** The UDP reply path does not recurse on nested data (`valueData` does not descend into data; `ofDataGo` and `writeGo` use explicit stacks). Require a work list, or refuse past a nesting depth.
6. **The turn's limit is `defaultSpace`, which is still to be tuned and is not in the record.** A crossing record writes its budget because replay depends on it; the space is the same kind of parameter. A separate frozen constant for turns, or write it in the record. A crossing guest may keep a turn's worth per waiting process, so the proposal should say the guest can still be ended.

## Other findings

7. The table was measured with the harness's `grown`, which charges 0 for checks, block ends and halts where the design charges 2; the delta quotes two of its figures as facts.
8. "It holds of every state the run is ever in" is true (space decisions do not depend on fuel) but that prefix lemma is not in the theorem list; `Ran.state` is used but not defined. The other statements are true and provable by strong induction on fuel with `omega`; `runSpace_full`, `runSpace_ledger` and `runIn_ledger` were checked against credit 0, cells 0 or 1, a count of 0, a charge above cells, halted and fault states, and `stepCost` 0.
9. The runtime count is not a function of `State`: two structurally equal states can be shared differently, so the deployed run is an instance of `runSpace sp` only for a per-run oracle.
10. The walk answers "too many" when `calloc` or `realloc` fails, so a reply can depend on allocator state; the image and the Linux process can then disagree, and `main.zig`'s second run can differ from its first.
11. The charge table matches `step`: at least what each case allocates, with no margin on `access`, `apply`, `cons` and the text case of `dcase`; no unbounded allocation is missed. `checkNat` reads as 3 in the source but the compiled C reuses the matched stack. The C counts a large number as its box plus `4 + bits/64` where `natCells` gives `4 + bits/64` for both.
12. Calling an out-of-space turn "unfinished" breaks no theorem (each is "if finished or waiting then"; every driver start state is running and drivers discard the returned state), but the text is wrong and raising the budget can never help.
13. Deltas: both MODIFIED requirements are faithful and their bases match. Three THEN clauses assert counts no export reports. "Adding tag 7 SHALL NOT change the bytes of any reply that had a form before" is false for an answer that no longer fits. "P3 is proved as a bound on the cells a run makes" overclaims: P3 is linear in steps, and `cons` onto a text makes unbounded cells in one step. "Cannot be for a measure of use" contradicts q59.74 in the same sentence. `defaultSpace SHALL be 8000000` is fixed while the design says it is to be set. `build` giving `81 07` over UDP needs 83M of the 100M steps at 8M. `reflect_live_cells` counts through constructor fields only; the wording is wider.
14. Stated as done but not: "`check-net.sh` … does so for a run out of space too", "No `sorry`, no new axiom", the proposal's "Proved", and "morphie's numbers … are under The default".

## `reflect_live_cells` as code

Memory-safe and terminating: load stays at or under one half, borrowed objects are untouched, all three failure paths free. `lean_nat_log2` is exported and allocates nothing here. Defects: the memory comment is wrong (finding 2); `cut + 1` wraps to 0 for `cut == SIZE_MAX`, unreachable through `Host.lean`'s half but the contract should say so or saturate; the hash keeps the low bits of the product, weak mixing, harmless at these sizes.

## Is the "no pure measure" argument right?

Yes, for any count that leaves the heap alone: the tree is exponential, and distinct parts under-counts. No cheap pure alternative was found that is sound and admits ordinary programs. The conclusion skips one option the design itself lists: q59.74, where the run makes the sharing rather than asking about it. Lean's runtime already ships that pass (`ShareCommon.shareCommon'`).

## Answered

Every finding is answered in `design.md` ("The advise read, answered") before any Lean was written. The read was not repeated on the revised design; the code is checked by the build, the contracts and the checks on morphie.
