# Reviews

## 2026-11-24, first read: send-back

Fresh context, Claude Opus 5.5 (subagent), given only this directory and the code paths (`net.zig`, `quic.zig`, `quic-client.zig`, `check-quic.sh`). "The mechanism is mostly sound against a truly off-path host. Three things must change before code." It found no attack by refusal cycling, token replay, routing collisions or the idle rule beyond M1 and S1, and called the Retry, token and duplicate-window handling otherwise correct against RFC 9000 and 9001.

| | Finding | Done |
|---|---|---|
| M1 | The guest answers to the source MAC of the frame that came in (`sendUdp`), so a host on the guest's Ethernet segment gets the Retry, and a valid token, for any IPv4 address it names, with no ARP. It can fill the address pool from made-up addresses, or hold `a_C`'s address slot. (A2) does not hold for such a host. | Design §1 adds (A0): the other host is not on the guest's segment; frames from beyond it come through a router whose MAC they carry. §6 and the spec's "what this does not give" state what a host on the segment can do, and the older hole of the same kind (`noteArp` takes any ARP reply for the peer). Binding the token to the MAC would not help: a bridge learns whatever source MAC a port sends. |
| M2 | Setting `validated` at admission skips the branch of `longPacket` that finishes the server's Initial space when a Handshake packet opens, so after every Retry the server would resend its padded ServerHello ten times. | Two fields: `validated` lifts the 3× limit; `hs_opened` finishes the Initial space (RFC 9001 §4.9.1) and is set only by a Handshake packet that opens. Exit 71 now also requires that a Retry exchange whose reply is acknowledged leaves the server with nothing to send; its control is the old coupling. |
| M3 | Nothing checks that a client refuses a Retry it must not take; an `onRetry` without its tag check would pass every planned check. | Exit 79: a second Retry, one after an Initial opened, one for another destination ID, with an empty token or one over 64 bytes, one whose tag was made with another original ID, and one whose source ID is the client's first destination ID (RFC 9000 §17.2.5.2) are each dropped. Controls: the tag check, the one-Retry rule, the opened-Initial rule and the destination-ID rule, each undone. |
| S1 | (A3) is not independent of X: queueing behind X's datagrams counts against C's cap; and an allowed entity's long run caps out every handshake in progress. | (A3) is stated with the queue in it, computed from the measured costs (§1). The guest's own time in a run is not charged to any cap: after a run, every connection not yet accepted has its start moved on by the run's length (`Table.pause`). |
| S2 | A refusal cycle costs the other host one X25519 product, not a signature: the name is checked first. | §5 corrected; the asymmetry is stated, and that such cycles are closed-loop, at most one in flight per slot the host holds. |
| S3 | The 2 s cap now applies with no attacker: a handshake that takes over 2 s on a bad path fails. | Stated in §6 and in the spec. |
| S4 | `orig_dcid` does three jobs; a token connection needs two values. | `Conn.tp_odcid` and `Conn.retried`. |
| S5 | A token Initial the address pool cannot take could use a free first-flight slot. | Taken: it goes there, validated. |
| S6 | RFC 9000 §7.3 also covers `initial_source_connection_id`. | The client checks 0x0f against the source ID of the server's Initial. The server does not check the client's 0x0f, as before; said so. |
| S7 | In `check-quic.sh`, an earlier step's connection may still hold a slot and put a `stall` client in the address pool from the host's own address, blocking the allowed client. | The flood and the stalled clients run on a fresh boot of their own, the stalled clients after the flood's slots have left. |

Notes taken: `retryTag` takes IDs of any length (the A.4 vector has none); `size` and `seal` carry the token in the header; the duplicate window wording is "the largest and the 63 below it" everywhere; exit 77 has a control per clause (time window, port, destination ID, MAC); the calling guest's Retry path is checked on real guests by a `check-wire.sh` run under a flood; "Mjolnir keeps working" is checked with the client of `e9a4c86` itself (`unikernel/compat/e9a4c86/`), not a flag that imitates it; the flood tool's arguments and the table's total memory are stated the same way everywhere.
