## Independent take (written before design/tasks/delta)

1. Pin: Zig never parses the program payload. One Lean export takes the program bytes and returns the whole reply. Anything Zig reads must be declared transport, not semantics.
2. Pin: the reply is bounded by one datagram. "Does not fit" must be its own outcome. The `main.zig` retry-by-rerun capacity pattern (which runs the program twice) must not be used per request.
3. Pin: a ceiling on the requested step budget inside the guest. Without one, a single request can hold a single-threaded polling guest indefinitely.
4. Pin: a closed binary outcome set (value, error, no result, bytes error, malformed request, too large) with fixed tags, separate from infrastructure failure.
5. Pin: request size is one unfragmented frame, so program bytes are about 1.4 KB. State this as a capacity limit, refuse anything larger, never truncate.
6. Pin: hardware. Modern virtio only. PCI config access stated. 64-bit BARs above 4 GiB mapped (`boot.S` maps only 0..4 GiB). MMIO uncached. Rings and DMA addresses bounded, with barriers.
7. Pin: a list of packet checks (MAC, ethertype, IPv4 version/IHL/length/checksum, fragments refused, UDP length/port/checksum, ARP only for our address). Every refusal drops the packet and never crashes.
8. Pin: the guest is stateless between requests, so UDP retransmission is safe and no reply cache is needed. Say what a native resource failure mid-request does.
9. Refuse: DHCP, fragmentation, any outcome decided in Zig, and a readiness signal that is not reached through the real service path.
10. Tradeoff: one-datagram UDP is simple to verify but caps program size. That is acceptable only with the cap stated and QUIC (q59.30) owning the rest. Acceptance means real CH 54.0/TAP, several programs to one guest, byte-equal to the Linux path, and survival after malformed packets.

## Comparison

The design answers most of the take, and does it well:

- **Transport vs semantics (1):** Zig reads only the RFL1 header (kind, status, ID, budget) and passes the remaining bytes unchanged to `reflect_reply_bytes`. The budget range and the "too large" decision are service policy and capacity, not language outcomes. No outcome is rebuilt from text. Ownership is coherent.
- **Capacity (2):** a fixed 1176-byte buffer, and the export returns the needed length with no rerun. This matches the take exactly.
- **Budget (3):** 1..100000000, with status 3 before evaluation. The design also states that a step is not a wall-clock bound (q59.9) and does not claim one.
- **Outcome set (4):** `[0, valueData v]`, `[1]`…`[6]` cover every `State` (`running`, `fault`, `halted` × `MOutcome`) plus decode failure and an unrepresentable value. The set is complete over `Reflect.Machine.State`.
- **Size (5):** the cap is 1200/1176 bytes, below the 1472 bytes that MTU 1500 would allow. The design explicitly forbids truncating output into a reply that looks valid.
- **Hardware (6):** CF8/CFC enumeration, capability-chain and BAR validation, BAR mapping from a bounded page-table pool, RAM-overlap checks, uncached volatile MMIO, VERSION_1 + MAC, split queues, 12-byte header, barriers, used-ID/length/outstanding checks, and a ring wrap test above 65536. This is stronger than my take.
- **Packets (7), statelessness (8), refusals (9):** all answered. Replying to the source MAC/IP avoids an ARP cache, and retransmission is documented as possibly evaluated twice.
- **Acceptance (10):** a real CH54/TAP guest, persistent across requests, compared byte for byte with the Linux path, using independently expected bytes, with malformed traffic followed by good traffic, an owned TAP that is cleaned up, and the existing image suite rerun. It is executable as written.

The unreachable hosts are not counted against the contract. The spike is explicit in `design.md` (Unverified hypotheses), it comes first in `tasks.md` ahead of implementation, and the design refuses to let native tests or a cross-compiled ELF stand in for it. That is the right gate.

## Findings (owed before accept)

1. **The delta spec relies on `design.md` for the frame.** The requirement "Framing supplies correlation…" says "the 24-byte RFL1 header defined in design.md". At fold, `design.md` is archived, so the living spec would point to an archived file. The spec also lacks the offsets, the magic, the kind values (0 run, 1 reply, 2 ping, 3 pong) and the full status table (0/1 reserved/2/3). Owed: copy the header table and code values into the requirement so `unikernel-net/spec.md` stands alone.

2. **The new export breaks the closed list in zig-host.** The living `zig-host` spec says "The exports that evaluate SHALL be `reflect_run`, … and `reflect_channels`". That is a closed list. `reflect_reply_bytes` evaluates, and the change has no zig-host delta. The sibling change `add-interpreted-run` handles the same situation with an ADDED requirement saying "`reflect_interp` SHALL be one of the exports that evaluate". Owed: add a zig-host delta, or a requirement in unikernel-net, that names `reflect_reply_bytes` as an evaluating Lean export under the same pointer/length/capacity contract. That makes the two folds compose. (The list already omits `reflect_vm_start`/`reflect_vm_from`, but that drift predates this change.)

3. **The outcome byte form has no home in Wire, and it is a third encoding.** The reply `[0, valueData v] | [1] | [2] | [3, i] | [4] | [5] | [6]` is a byte form of a machine outcome. It is independent of the network, and q59.16 (closure exchange) and Mjolnir callers will decode it. Today it would be specified only in `unikernel-net`, and the design does not name the Lean module that defines it. It also differs from `Reflect.reifyOutcome` (`[0, v] | [1, i] | [2]`, `Semantics.lean:167`), which `Surface.unreifyOutcome` already reads back. Owed, either of:
   - (a) put the encoder in `kernel/Wire/Form.lean` (for example `Wire.outcomeData`) with an ADDED `wire-bytes` requirement "A machine outcome has a byte form", leaving `unikernel-net` to say only that the reply payload is that form;
   - (b) state in the delta why the reply form is local to the network, and why it does not reuse the `reifyOutcome` tags.

   Either way, name the Lean definition the tests decode against.

4. **Request handling is ambiguous for well-formed frames with the wrong fields.** The design drops "unsupported kinds" and "malformed headers" without saying which kinds a server accepts. It does not say what happens to:
   - a request of kind 1 or 3;
   - a ping with a nonzero budget or a payload;
   - a run or ping with a nonzero status.

   Owed: the spec states that the server accepts only kinds 0 and 2. Every other combination is dropped without evaluation and without a reply, except a run with status 0 and a budget out of range, which gets status 3. The malformed-traffic scenario includes one example of each.

5. **Feature negotiation is written as a deny-list, and RX buffer size is unstated.** The spec says "without offloads or merged RX buffers". The design lists features to decline. Owed:
   - phrase it as an allow-list: the driver sets exactly VERSION_1 and MAC, and never sets ACCESS_PLATFORM, CTRL_VQ, MQ, RING_RESET or any other bit;
   - startup fails if the device does not offer VERSION_1 or MAC;
   - RX buffers hold at least 1526 bytes (12-byte header + 1514), as VIRTIO 1.2 §5.1.6.3.1 requires without MRG_RXBUF;
   - a used length greater than the posted buffer is a drop, not a copy.

6. **What happens when a request kills the guest is unstated.** The design says "a hardware fault still stops the guest". A Lean allocation failure, `lean_panic`, or guard-page fault during a request is reachable within the budget. For example, repeated bignum squaring can exhaust 512 MiB in a few dozen steps (q59.9). Mjolnir needs to know what that looks like. Owed: one requirement and scenario. On any abort mid-request, the serial port names the cause and the VMM process exits nonzero (or powers off with a stated status). The service never re-announces readiness from that boot. The client reports a timeout, not an execution result. The check exercises one such request and confirms the guest's death is observable.

7. **A spike result that changes the contract is not routed back.** The spike may show that CF8/CFC, the BAR placement, or the page attributes differ from the design. Owed: a line in `tasks.md` saying that a spike finding that contradicts the hardware contract amends the change and reopens "Fresh advise after preparation" before implementation. A spike that passes goes straight to implementation.
