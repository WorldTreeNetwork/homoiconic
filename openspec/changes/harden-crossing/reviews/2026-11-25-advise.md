# Advise read of harden-crossing (Opus, fresh context, 2026-11-25)

Read of the design before any code. Answered in `design.md`, "The advise read, answered".

**Verdict: send-back**

The budget agreement (D-1) and the acknowledgement-order check are sound. I traced both against `Surface/Cross.lean` and `net.zig` and found no honest pair either would refuse. The root choice is also justified: `valueData`, `reify`, `decomp` and `codeFits` already have `@[csimp]` walks, while `Wire.save`/`cut` recurse once per level of nesting.

The hold, though, does not deliver what q59.71 asks. A record can still outgrow its buffer, so the run halts with no record. One entry can make about twice what the memory sum allows. And the count cannot see one of the places a lying peer can make a guest hold memory.

## Findings

**1. Blocker: a full guest's record does not fit 16 MiB, so the run halts with no record.**
- **The problem.** D-3 says "with the ledger's charges it fits in 16 MiB". It doesn't, because each count resets the credit to `H - m`, and `m` counts objects once each.
  - **The log.** An entry holds about 3 objects: a list cell, a `Note` and an `Event`. Charging `entryCells` = 32 doesn't change that, because counts give the charge back. So a guest reaches the bar (1.5M) at about 500k entries.
  - **One entry line** is about 110 bytes, since `entryName` is a 256-bit number printed in decimal (`Keep.lean:645`).
  - **A trivial infinite local ping-pong** therefore ends `full` with a record of about 55 MB.
  - **Shared values make it far worse.** A local `did (spawn i)` passes the parent's data object to the child unchanged. N children that each finish with the same result of 4000 bytes count that result once but print it N times. About 75k children gives a record of about 300 MB.
- **What happens.** `net.zig:754` `halt("the record does not fit")`, after Lean has built the whole string and its `toUTF8` copy. The worst programs end with no record, the opposite of "its own outcome in the record".
- **Suggested fix.**
  - Add a pure entry cap that the replay checks exactly, ending in `full` or a new body.
  - Make each process line fixed-width: kind, a digest of the status data, and the root.
  - Bound or hash the `holds` list on each line.
  - Then derive the buffer size from the cap.

**2. Blocker: the worst single entry is four runs of up to `turnSpace` each, not "two turns".**
- **The problem.**
  - **One turn is two runs.** `turnRun` is `runTurn` on the resume, then `settleRun`, which is another `runTurn` on `payloadTerm` (`Channel.lean:225-239`). A request closure written as `fn s -> s (build …) k` builds a fresh payload of up to 4M cells inside `settle`, and that payload is held. So one `turnRun` can leave up to about 8M cells held.
  - **comm** is two `turnRun`s: up to 16M cells.
  - **spawn** is the child's run and `settle` plus the starter's `turnRun`: four runs again. A local spawn also adds `unreify`/`compile` of a program as large as a payload (up to 16 MB written), which `codeCells` puts at about 4 × its cells.
- **Why it matters.** D-2 puts the worst at `H + 2 × turnSpace` = 240 MiB. With 16M or more cells in one entry, it is over the 360 MiB `mmap` area at 24 bytes a cell. `add-space-budget` measured about 233 MiB peak for about 3–4M cells (`build`), so the real cost per cell is higher still.
- **The tests miss it.** `cross-grow` and `cross-fan` grow slowly. Neither is the worst constructible program the task names.
- **Suggested fix.**
  - Redo the sum per entry kind.
  - Add a `cross-worst.hom` that starts just under the bar, then does one local comm where both sides build the most they can in both resume and settle. Run it on the image.
  - If it panics, the crossing needs a smaller turn space. That means the `turn` word with a space argument through `stepRun`/`schedRun`/`beginRun` (existing drivers pass `turnSpace`), or a lower `turnSpace`.

**3. Blocker: the count does not see `sent`, so a lying peer can exhaust memory.**
- **The problem.**
  - `reflect_live_cells` counts an object whose tag is above `LeanMaxCtorTag` as one cell and does not walk its fields (`ffi.c:134-136`). Arrays are such objects.
  - `Guest.sent` is an `Array Data` (`Cross.lean:82`).
  - A peer can send `[2,k]` for each crossing while never advancing `got`. The out-limit counts unacknowledged crossings, so the guest keeps putting out packets of up to 6000 bytes, and `sent` grows without end.
  - Each packet is charged once. The next count doesn't see it and gives the credit back.
- **Why it matters.** D-2's "a peer that never counts makes `sent` grow only with entries this guest made and charged" is false in effect.
- **Suggested fix.** Make `sent` a `List`, or walk array elements in the count. Also add a plain limit on uncounted packets (for example `sent.size - counted ≤ 2 × outLimit`) at which the guest stops producing packets.

**4. Should-fix: `cross-check.zig` would refuse every form-2 record.**
- **The problem.**
  - `signed()` requires the body to begin `me <name>\n` (`cross-check.zig:121-124`). D-4 puts `form 2` first, so every record would be refused with "it is not signed by the entity it names".
  - `out` is 2 MiB (`cross-check.zig:39`), but `reseal` writes a whole record into it, up to 16 MiB. The check's output (schedule plus `renderProcs` of full values) can also pass 2 MiB.
- **Suggested fix.** Look for the `me` line after `form`, and grow `out` too. D-5 currently lists only the record buffers.

**5. Should-fix: the order of checks moves an existing test's reason, and the spec and a control still assume the old one.**
- **The problem.** `CrossCheck.lean:104` "the takings in another order" swaps `a`'s takings. With the acknowledgement-order check run before the replay (spec: "combine…, require acks…, replay…, compare"), that test is now refused by acknowledgement order.
  - The `unikernel-net` delta still credits it to "(the comparison)".
  - The `cross-controls.py` control "the processes are not compared" names that test, and would report NOT SHOWN.
- **Suggested fix.** Re-credit the test and its control, or keep it as the acknowledgement-order test.

**6. Should-fix: big results and payloads become less checked than now.**
- **The problem.**
  - Today `procLine` prints a finished value or payload in full.
  - Under the change, one above 4096 written prints only a fixed text. If its process also gets `root none` (over `procRoom` 1M, or after `sideRoom`), nothing compares it. Results up to 16 MB written are allowed (`runTurn`'s `writes (4 * turnSpace)`).
  - The rule for `sideRoom` is also ambiguous. If each process tried uses all of `procRoom`, only the first 8 processes ever get a root.
- **Suggested fix.**
  - Always put a digest of the status data on the line. Data is bounded and needs no room. Keep the room for the function's tree form only.
  - State that a process uses `min(used, procRoom)`.
  - The proposal says such values are printed "as their size" and the design says `a payload of more than 4096`; pick one.

**7. Should-fix: charging after `full` is undefined, and an honest full guest is refused.**
- **The problem.** A full guest still records acknowledgements, and each is charged `entryCells` against a spent credit. `Hold.walk` rule 1 then demands a count, while rule 4 forbids anything but an acknowledgement after `full`.
- **Suggested fix.** No charge and no credit after `full`. Say so in D-2 and in `Hold.walk`.

**8. Should-fix: the list of what a lying guest can still do is incomplete.**
- **Missing: it can get an honest peer's record refused, and the reason can name the honest side.** It can put out a packet whose message or `held` differs from what its log replays to, send `[2,k]` for a crossing never taken, or withhold an acknowledgement. The check cannot tell who lied. State this.
- **Missing: it can lower the honest guest's budget to 1.** Every turn is then unfinished. This changes the run's outcome, not only its liveness.
- **Missing: it can force the honest guest `full`.** It can fill the queue with 128 packets of 8 KiB (`pending` is counted), or start children on it.
- **Missing: it can grow `sent` without bound,** until finding 3 is fixed.
- **Missing: it can make the check's cost unbounded.** The hold it states is unchecked, so its log and replay are unbounded. The check should have its own ceilings (`budget ≤ budget_max`, `hold ≤` a maximum, a maximum record size). That is also the honest reading of "the check must check what the replay needs". `budget ≤ limit` is only self-consistency.
- **One claim needs restating.** "Cannot run with another budget" should read "cannot hand over a record with another budget".

**9. Should-fix: gaps in the tests and controls.**
- **Untested mechanisms.** `outLimit`, `queueLimit`, trimming of `sent`, lines over 4096, and `root none` have no tests. Each needs one, with a control. For example, a crafted batch of 200 packets should leave `got = 128`.
- **"A count moved" is caught by two rules** (spent and not counted, and a count where nothing was spent). It cannot credit either rule alone. Name a test per rule that only that rule catches: a count dropped, a count inserted.
- **`cross-grow` needs to stop on its own.** With the guest's ledger undone in Lean it would grow until `cross-controls.py`'s 300 s timeout, which the script reports as a broken control, not a failing test. It should stop after a known number of turns, with a separate unbounded variant for the panic control on the image.
- **`cross-hidden` must trigger no counts.** Otherwise the swapped log can be refused by `Hold.walk` before the root ever decides it.

**10. Note: the check's measured replay is not yet covered by `accepted_network`.** The check would run a replay interleaved with `combineTrace` and charging. A theorem at schedule level (this walk's final configuration and outcome equal `schedRun`'s) is needed, or `accepted_network` no longer speaks of what the check ran. Add it to D-6.

**11. Note: `did (answer i x)` has no row in the charge table.** A lying record can contain one; define its charge or refuse it.

**12. Note: at the out-limit the guest must keep doing other work.** When `pick` gives a far spawn at the limit, `act` must hide that process and choose again, not return `none` (`Cross.lean:232`). Otherwise all local events stop.

**13. Note: `queueLimit` = 128 is exactly the honest bound (64 + 64).** Define it as `2 * outLimit` so a later change can't break honest pairs.

**14. Note: the memory sum leaves things out.**
- The queue between counts: up to about 2M cells once parsed.
- The record built at close: the string, its `toUTF8` copy, and the chain's data.
- A 16 MiB static `record_buf`, which shrinks the `mmap` area.
- The time to print 16 MiB on serial against the 90 s wait in `check-wire.sh`.

**15. Note: a simpler, stronger root is possible.** A Merkle hash computed with a work list, memoised by pointer through `implemented_by`, removes `root none`. A hash of each side's process roots then gives the per-side hash the task literally asks for. Separately, a run nonce in both records would stop pairing records of two runs in general, not only runs that differ in delivery order.

**16. Note: wording.** Fix side `b`'s budget when it first runs anything, not at its first entry. This is harmless as written, but simpler to state.

## Claims I checked and found sound
- **D-1 agreement holds for honest pairs.** In `net.zig` the caller is `b`, and `a` begins only in `crossSettle` or in its own `work` after `heard`. In both orders of handing over the program and the first batch, `a`'s fixed budget `B` is at most every value `b` announced, and `b` lowers to `B` in `take` before any packet is worked. One condition: `a` must count as not idle until it begins.
- **The acknowledgement-order check refuses no honest pair.** Packets are taken in `seq` order, `inbox` is worked in order, and `[2,k]` is posted at the taking. A full guest still records acknowledgements.
- **The replay can recompute every charge:**
  - `out` comes from the asker's state at its place in the walk.
  - A taking comes from the other half of `stepMade`. Its packet is rebuilt from the asker, whose held names are unchanged between `out` and the taking.
  - `a`'s begin comes from `beginMade`.
- **The listed theorems are provable.** They are mostly definitional: the existing four with the two new entries, `combineTrace_walk`, and the `_fst` theorems, which mirror `runSpace`'s two shapes.
