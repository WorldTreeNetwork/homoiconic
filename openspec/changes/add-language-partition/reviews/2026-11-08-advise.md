## Blind independent take

Written before opening design.md or tasks.md, using only proposal.md's Why (line 11) and the packet's stated absence of a living spec and product code.

1. Pin Lean 4 source as the single authority for circular evaluation semantics.
2. Pin the running evaluator to that same definition so the proof cannot silently describe a separate model.
3. Pin Zig's responsibility to hosting the process and invoking Lean, with a boundary that is reviewable.
4. Refuse evaluator logic in Zig, including fallback interpretation that could bypass the Lean definition.
5. Refuse Rust as a first-system implementation dependency; additional type checking does not establish the Lean theorem.
6. Require a clear distinction between theorem claims about Lean definitions and assumptions about compilation and foreign calls.
7. Require an ownership boundary that prevents host-side representation or conversion from acquiring evaluation semantics.
8. Require an observable way to verify the language partition when implementation lands, without claiming it already exists.
9. Keep concrete kernel and host implementation work outside this architecture decision while identifying their obligations.
10. Accept the tradeoff of a Lean/Zig integration boundary to retain one semantic definition, provided that boundary's limits are explicit.

## Comparison with the authored contract

The core partition answers take lines 1–5 directly. `design.md:5–8` assigns evaluation to Lean, hosting to Zig, and excludes Rust. The delta makes those assignments normative in `specs/language-partition/spec.md:5`, `:15`, and `:31`. In particular, the prohibition is against an evaluator in Zig, not merely against a function whose name is `eval`. The narrower source-review scenario at delta line 27 should be read under that prohibition.

The proof claim is appropriately about Lean source. `design.md:7` and delta line 41 narrow the first theorem to metacircular equality on a named small fragment. They do not promise correctness of all programs or of the compiled process. This substantially answers take line 6: the source-level claim is clear, although compiler, runtime, and foreign-call assumptions still need concrete treatment when those artifacts exist. The phrase “proof boundary is the call” (`design.md:16`) is an architectural boundary, not evidence that the call or the Zig caller is verified.

Take lines 7–8 are answered at the level this node can support: delta lines 15–27 require delegation and preservation of the kernel's result, while `design.md:28` explicitly records that ABI feasibility is untested. The host change must settle representation conversion, allocation ownership across the Lean runtime, and failure behavior without moving evaluation into Zig. “Allocation in Zig” is the host responsibility; the same design explicitly loads the Lean runtime and does not establish that every runtime allocation is performed by Zig. Those details belong to the downstream ABI work, not an invented interface in this ADR.

Take lines 9–10 are answered by the separation in `design.md:24` and the two tasks. The act owes `ARCHITECTURE.md`; the kernel and host remain separate changes. The delta's runtime scenarios are future conformance obligations, not claims that the empty product tree has already passed runtime checks. The named-fragment metacircular acceptance criterion is carried consistently from the design to the delta and the ADR task.

## Steelman against the blind take

My initial concerns could demand an ABI specification, execution evidence, or a compiler-correctness argument before permitting a language choice. That would exceed this node's purpose. The strongest case for the authored approach is that it first fixes semantic ownership, then makes the integration hypothesis explicit and assigns it to the change that can test it. That sequencing prevents an implementation experiment from quietly creating a second evaluator while avoiding a speculative interface contract here. The remaining integration uncertainty is real, but disclosed and bounded; it does not contradict the partition decision.
